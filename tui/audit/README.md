# The audit harness

Evidence for the owner's UI and UX policy and this product's [profile](../../docs/ux-profile.md) (the project policy's [section 3.3](../../docs/UI-UX-POLICY.md)), one command per job, never touching your bot's data, services, desktop or browser. Run it from `tui/` with the screen's venv:

```bash
cd tui
.venv/bin/python -m audit <job> --out DIR [options]
```

Every run first reads your real home from the password database and refuses to start if any path it will use (symlinks followed, `--out` included) is in `~/.local/share/tele-notify*`, the corpus folder, `~/.config/tele-notify`, `~/.local/lib/tele-notify`, the installed `~/.local/bin/telenotify` and `telenotify-tui`, `~/tele-notify` or `~/Projects/bqtechjobs`. It then works in its own new folder `/tmp/tn-audit/<run>/` (deleted at the end): a temporary `HOME`, a tiny synthetic `config.json` (no `api_id` / `api_hash`), `data_dir`, labels and corpus inside it, `PATH` = the fakes folder + `/usr/bin:/bin`, and an environment built from scratch (no `DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`). Fakes stand in for `systemctl` (answers per service: active, inactive, failed or missing; logs every call), `xdg-open`, `gio`, the browser (`$BROWSER`) and `telenotify` (`--bin repo` uses the repository's build instead). The fakes' call logs are copied to `DIR/fake-calls/`. Data is synthetic only (`audit/data.py`). The test suite's autouse fixtures are not used: `DECIDE_DELAY` is real.

Every job ends with a leak scan (`DIR/leaks.json`): any file holding your login name or real home path makes the command exit 3. `DIR/run-<job>.json` records the screen's commit and the machine's load.

The large master file is built once (about 10 s) and never opened for writing: each timing or interactive run copies it into its own scratch folder. It is rebuilt when its manifest no longer matches (size, schema version). On a shared machine run heavy jobs (`timing`, `big-state`) through the memory guard you use for builds.

**Another checkout.** `--app PATH/tui` audits that checkout's screen with this harness, so task costs and timings can be taken on main and on a branch: `git worktree add /tmp/main-wt main`, then `python -m audit tasks --app /tmp/main-wt/tui --out A` and again without `--app`, and diff the tables. `timing --compare /tmp/main-wt/tui` interleaves the two checkouts' runs.

**Real terminals** (`terminal`): what the SVG screenshots can't show — the terminal's own font, colours as drawn, its Arabic shaping and cell grid. Each shot starts a fresh terminal window running the real screen on the usual sandbox (fresh synthetic state each time), inside a headless GNOME compositor of the job's own: `mutter --headless` with Xwayland, in `dbus-run-session`, with a private home, runtime folder and D-Bus session in `/tmp/tn-audit/<run>-term/` (deleted at the end; a folder left by a run that was killed is swept at the next start). Your desktop's `DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `XAUTHORITY` and `XDG_RUNTIME_DIR` are never passed on. The session's bus has no service files at all, so it starts nothing on demand (no portals, document store, gvfs or accessibility bus); GTK and GIO are also told not to use portals or gvfs. kitty runs as an X11 client with `--config NONE` (its defaults, 11 pt), sized in cells; Ptyxis runs as a separate instance (`-s`) with its settings in a private keyfile (size in cells, Monospace 11, its style following the theme). Ptyxis asks `systemd-run --version` whether to start each tab in a systemd scope; the session has no user systemd (and never reaches yours), so a stand-in first on the session's `PATH` logs the call and says no, and Ptyxis starts the tab itself (asked to run a command, the stand-in runs it without a scope). Every process the session starts carries a mark in its environment: at the end of each shot that shot's processes are ended (the terminal's helper and the screen run in sessions of their own), and at the end of the run mutter is stopped first (so Xwayland removes its display lock and socket), then everything else; a lock or socket still left is removed if it is yours and its process is gone. Cleanup isn't cut short by a signal. Without `--bidi` each terminal gets what the screen's auto mode picks there (kitty `words`, Ptyxis `full`). The window is captured with ImageMagick `import -window` (metadata stripped). Needs `mutter`, `Xwayland`, `dbus-run-session`, `xdotool` and ImageMagick.

- *Covered:* the screen as it first opens on each tab (`1-dashboard`, `2-review` after the decision delay, `3-search`, `4-settings`) and the keys panel (`keys-panel`), per terminal, size, theme, mode and bidi mode. Nothing is typed or clicked: the screen (a harness child) switches theme and tab in-process, as the `1`–`4` keys and the theme setting do, and reports its size, theme, tab and whether the keys panel is open; a shot in another state than asked for is an error. Next to each PNG: the screen's own SVG and text of the same moment (`.svg`, `.txt`).
- *Not covered:* dialogs, drop-downs, search results, toasts, focus moves, the mouse and anything after input; OSC 52 copying. Those stay with the SVG screenshots and the owner's check.
- *Contrast reading:* for kitty with its defaults (no padding or title bar, so the cell grid's place is known), `rows_read` in the index reads the header's and footer's cells as drawn (the cells the screen says they cover: a docked panel narrows the footer), cell by cell: each run of text with its ink and background and their contrast, rounded down. `min_contrast` is the lowest for text (the summary names it); runs of thin glyphs only (anti-aliasing keeps `.` or `/` from reaching their colour) are left out, and box-drawing lines and blocks (the footer's `▏` divider) have their own `min_graphic_contrast`. A lighter glyph inside a word (strokes between pixels) is read with its word; a word in a dimmer ink (a dimmed key) keeps its own run. It is a reading, not the R6 measure (the `colours` job).
- `--kitty-config PATH` draws kitty with your own `kitty.conf` (font fidelity; the window size and X11 are still set by the job). The file itself is refused in the protected places (symlinks followed), but kitty also reads what it names with `include`, `globinclude`, `envinclude` and `geninclude` (the last one runs a Python file): the job doesn't follow those, so use a kitty.conf whose includes you know. Your `~/.local/share/fonts` is linked read-only into the private home so its fonts are found.
- The leak scan reads a PNG's text chunks (decompressed, at most 64 MiB each), not its compressed pixels, which are noise to a byte search, and says which chunk a hit is in; a file that isn't a well-formed PNG to its end is read whole. Text drawn as pixels can't be read from a PNG: the `.svg` and `.txt` next to it hold what the screen drew, and the scan reads those.
- It is heavy (mutter and a terminal: about 1–2 GB, and a few seconds per shot): run it through your memory guard, e.g. `memjob 3 .venv/bin/python -m audit terminal --out DIR` (the guard first: it needs your real user bus, which the job itself never passes on).

**Interactive mode** (the owner's sign-off): `python -m audit interactive [--bidi full|words] [--size-check] [--real] [--big]` starts the real screen in your terminal on the same kind of run folder, with every isolation above (Start / Stop / Restart reach only the fake `systemctl`), on the plain synthetic data. Only the terminal's own variables (`TERM`, `COLORTERM`, `KITTY_WINDOW_ID`...) are kept so it draws as it would for you. Without `--bidi` the screen picks the mode for your terminal.

Tests for the harness itself: `tests/test_audit.py`. The `terminal` job's live smoke test (one kitty shot) runs only with `TN_AUDIT_LIVE=1` and mutter, Xwayland, xdotool, ImageMagick and kitty installed; the rest need no display.
